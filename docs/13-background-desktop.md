# 后台桌面操作能力 需求文档

> 状态：讨论稿，待确认
> 日期：2026-11-07
> 范围：`dsh-orb` 插件（悬浮球 + 后台 agent），不改变前台 Computer Use 模式
> 本文只描述产品形态与需求，不涉及技术实现

## 1. 一句话

让后台 agent 能像人一样操作桌面软件，但默认不碰鼠标、不抢窗口；用户在用电脑时它隐身，需要时它"举手"，举完放下；它不能向用户提问，所有需要用户决定的事交回前台。

## 2. 背景与问题

当前悬浮球有两个角色：

- **前台 agent**：Computer Use 模式，能看屏幕、能操作软件，但必须占用屏幕和鼠标，用户只能等它做完。
- **后台 agent**：标准模式，能读写文件、跑命令、上网，**碰不了界面**。

结果是一个长任务被切成两半：后台把文件做完，停下来，通知前台；前台再切回界面部分一步步点。用户看到的就是"它做一会儿、停一下、再动一下"。

问题不在后台不够聪明，在于**后台没有一双手**。

## 3. 目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 后台能独立完成包含界面操作的任务 | 一个"写文档并发出"的端到端任务，全程不需要前台接手 |
| G2 | 后台操作界面时，不打断用户正在做的事 | 用户不切换窗口、不丢焦点、不丢正在进行中的输入 |
| G3 | 用户装完插件即可使用，零额外操作 | 不下载附加组件、不安装运行时、不配置路径、不出现命令行窗口 |
| G4 | Windows 与 macOS 体验一致 | 同样的任务在两边都能完成，用户流程相同 |

## 4. 非目标

- 不改变前台 Computer Use 模式的任何现有行为与体验。
- 不做第二套"后台截图识别"方案；后台对界面的理解只依赖软件暴露的结构化信息，不依赖像素。
- 不突破系统权限：系统不允许的操作就是不允许，不采用非常规手段强行置前或提权。
- 不做远程控制、不做多设备、不做无人工厂。
- 不替用户做不可逆的决定（见 D6）。

## 5. 用户与场景

**场景一：从文档到发出**
用户说"把这份资料整理成 Word，发给张老师"。
后台写完文档，直接在办公软件里打开、排好格式、保存；再在该沟通软件里找到人、附上文件、发出。全程用户可能正在浏览器里看别的东西，屏幕上只有一次短暂的目标窗口置前。

**场景二：批量整理**
用户说"把这批发票按月份归档到对应文件夹"。
后台打开文件管理器，新建文件夹，逐个移动。文件管理器全程在后台，用户不被打扰。

**场景三：做不到的时候**
后台需要操作一个用户正在打字的软件。
它不碰那个软件，先换一条路（改用文件、命令、另一个软件）；都不行，就停下，把"我需要在这个软件里点一下发送，但用户正在使用它"交回前台；前台向用户确认后，或者自己完成，或者给后台一次临时许可。

## 6. 产品形态

- **两个模式并列存在**：前台 Computer Use 模式（不变）、后台桌面模式（新增）。
- **后台模式 = 标准模式的全部能力 + 桌面操作能力**。它仍然是一个可以读写文件、跑命令、上网的工作会话，只是多了一双手。
- **用户通过前台发起**：用户在悬浮球里提出需求，前台判断这段活适合交给后台，就派给后台。用户感知上是"这件事交给它去办了"，而不是"我要手动开一个新模式"。
- **模式在选择器里可见**：用户也能自己新建一个后台桌面模式的会话（不是隐藏能力）。
- **安装即用**：装完插件，两个模式都可用。没有第二次下载、没有安装向导、没有环境配置。
- **平台**：Windows 与 macOS。

## 7. 核心需求

### A. 能力

| 编号 | 需求 |
|---|---|
| A1 | 后台模式必须具备标准模式的全部能力（文件、命令、网页、技能等） |
| A2 | 后台模式必须具备桌面操作能力：查看软件界面结构、点击、输入文本、按键、滚动、等待界面变化、打开/关闭软件、切换窗口 |
| A3 | 后台的操作对象是"软件里的可操作元素"，不是屏幕坐标；同一元素在不同时刻应能被稳定识别 |
| A4 | 界面变化后，旧的定位信息必须失效，不得凭旧信息继续操作 |

### B. 静默与边界

| 编号 | 需求 |
|---|---|
| B1 | **默认静默**：不移动鼠标、不抢键盘焦点、不切换前台应用 |
| B2 | **不得操作用户正在使用的软件**。判定：该软件位于前台，且用户近 60 秒内有过键盘或鼠标操作 |
| B3 | 同一时刻，同一个软件只允许一个后台任务操作；不同软件可以并行 |
| B4 | 前台模式正在操作屏幕时，后台不得介入；后台正在操作某个软件时，前台也不得抢同一个软件 |
| B5 | 后台不得读取剪贴板、系统通知等与当前任务无关的用户内容 |

### C. 举手（临时置前）

| 编号 | 需求 |
|---|---|
| C1 | 只有在无头方式**确认做不到**时才允许举手：控件不可用、界面结构读不到、或系统明确要求窗口在前台 |
| C2 | 举手由后台 agent 自主决定，但必须是一次显式动作，会话记录里可见 |
| C3 | 举手的前提是用户空闲（2 秒内无键鼠操作）；用户正在操作时不得举手 |
| C4 | 举手只把目标软件置前；仍然使用结构化信息操作，不移动鼠标、不模拟按键 |
| C5 | **用户一动就放下**：举手期间用户一旦有键鼠操作（2 秒内），立即放弃该软件上的操作并把前台还回去 |
| C6 | 举手是临时的：任务段结束、主动放下、或超时（90 秒）自动放下；放下时把前台还给原本在前的软件 |
| C7 | 举手必须限流：单次任务内的次数与间隔受限，避免窗口反复跳动 |
| C8 | 举手失败（系统不允许置前）时，不得使用非常规手段强行置前；转为等待用户点一下，或直接回传前台 |

### D. 不提问与回传

| 编号 | 需求 |
|---|---|
| D1 | **后台模式不包含"向用户提问"的能力**，该能力在后台模式中不存在 |
| D2 | 需要用户决定、或无法继续时，后台必须先尝试不依赖受阻软件的替代路径（改用文件、命令、其他软件）；全部不可行才停止并回传前台 |
| D3 | 回传内容必须包含：做了什么、卡在哪、为什么需要用户、可选方案、风险提示 |
| D4 | 回传后由前台向用户提问，并决定后续：前台自己完成，或给后台一次临时许可 |
| D5 | 临时许可只对指定软件、只对本次任务有效；任务结束、超时、用户收回即失效 |
| D6 | 不可逆操作（发送消息、删除、支付、覆盖保存、关闭有未保存内容的文档）默认不得由后台自主执行，必须走回传 |

### E. 可见性与控制

| 编号 | 需求 |
|---|---|
| E1 | 用户能看见后台正在操作哪个软件、在做什么（会话记录可读） |
| E2 | 用户能随时停止：一个动作停掉当前后台任务，正在进行的界面操作立即中止 |
| E3 | 举手时用户有可感知的提示，而不只是窗口跳了一下 |
| E4 | 所有界面操作留痕，可在会话里回看 |

### F. 安装与平台

| 编号 | 需求 |
|---|---|
| F1 | 安装插件后两个模式都可用，不需要任何额外下载、安装或配置 |
| F2 | 全新 Windows 机器（未修改系统安全设置）与全新 macOS 机器上，用户流程一致 |
| F3 | 不出现命令行窗口，不要求用户设置路径或环境变量 |
| F4 | 卸载插件后不留下全局残留 |

### G. 数据与隐私

| 编号 | 需求 |
|---|---|
| G1 | 只读取完成当前任务所需的界面内容；不上传任何界面内容 |
| G2 | 界面内容可能含隐私，日志默认不记录具体内容 |
| G3 | 用户可关闭"后台桌面操作"开关；关闭后后台退回纯文件/命令模式 |

### H. 稳定性

| 编号 | 需求 |
|---|---|
| H1 | 单个界面动作一般在数秒内完成；长时间等待必须对用户可见 |
| H2 | 操作失败不得让任务卡死，必须有超时与明确的失败结论 |
| H3 | 系统不允许的操作不得反复重试刷屏 |

## 8. 状态与规则

| 目标软件位置 | 用户状态 | 存在前台任务 | 后台可以做什么 |
|---|---|---|---|
| 后台 | 任意 | 无 | 直接操作（静默） |
| 后台 | 任意 | 是，且是同一软件 | 等待，不得介入 |
| 后台 | 任意 | 是，但是别的软件 | 直接操作 |
| 前台 | 空闲 | 无 | 先换替代路径；不行则举手 |
| 前台 | 活跃 | 任意 | 不操作、不举手；换替代路径，不行则回传 |
| 前台 | 任意 | 是 | 不操作、不举手；回传 |

## 9. 主流程

**流程一：全程后台**

```
前台派活 → 后台读写文件 → 后台在后台的软件里操作 → 完成后回传结论
```

用户屏幕无变化。

**流程二：需要举手**

```
后台发现无头做不到 → 检查用户是否空闲
  → 空闲：举手 → 操作 → 放下并还原前台
  → 不空闲：换替代路径，不行则回传
```

**流程三：举手后仍不行**

```
举手 → 仍然失败 → 放下 → 换替代路径 → 都不行 → 回传前台
```

**流程四：用户确认之后**

```
前台向用户提问 → 用户同意
  → 前台自己完成
  → 或给后台一次临时许可，后台在该软件上继续，任务结束即失效
```

## 10. 用户可见文案（示例）

- 后台开始操作：「后台正在处理：在 Word 里排版」——只说软件和动作，不暴露界面内容。
- 举手前（若用户在设备旁）：「需要把 Excel 切到前面几秒」。
- 用户一动就停：「检测到你在操作，已暂停」。
- 交回前台：「这一步需要你确认：在微信里给张老师发送《报告.docx》。后台已停下，等你决定。」
- 权限/能力不可用：「这台电脑的系统设置不允许后台操作其他软件」。

## 11. 验收标准

1. 用户正在 Word 里打字时，后台任务需要操作 Word → 后台不操作，先走替代路径；全部失败则在会话中产生一条回传，前台向用户提问。
2. 后台需要操作一个在后台的 Excel → 直接操作，屏幕无变化（除 Excel 自身内容）。
3. 后台无头操作失败 → 举手 → Excel 置前 → 用户碰一下鼠标 → 立即停止操作并把前台还原。
4. 用户在打字期间后台需要举手 → 不举手，等待或回传。
5. 后台全程不出现任何提问卡片（该能力不存在）。
6. 任务段结束 90 秒内未放下 → 自动放下并还原前台。
7. 后台尝试对"发送消息"类不可逆操作 → 停下并回传，不自行执行。
8. 全新 Windows 机器 + 全新 macOS 机器：装完插件即可完成一次"打开软件 → 输入文字 → 保存"的任务，无额外下载。
9. 断网状态下，两个模式都能使用。
10. 会话记录能看到后台操作过哪些软件、做了什么。
11. 关闭"后台桌面操作"开关后，后台无法碰界面，且任务不会因此卡死。

## 12. 已经定下的取舍

1. **不提供"始终允许"设置。** 后台对不可逆操作一律停下回传；用户每次都要在前台确认。
2. **举手提示只写进会话记录**，不弹系统通知、不在悬浮球上弹卡片。用户想回看时，在会话里能看到"举起了哪个软件、什么时候、做了什么"。
3. **"用户正在使用" = 前台 + 近 60 秒有输入。** 60 秒覆盖打字、阅读、滚动之间的停顿；用户离开一分钟以上，才允许直接操作前台窗口。
4. **"刚离开电脑"按 60 秒空闲处理。** 空闲满 60 秒即视为离开，可以直接操作前台窗口，不需要先举手；但举手本身仍要求 2 秒内的安静，避免打断正在落下的一次按键。

## 13. 术语

| 术语 | 含义 |
|---|---|
| 前台模式 | 现有的 Computer Use 模式，占用屏幕与鼠标 |
| 后台模式 | 新增模式：标准能力 + 桌面操作能力，默认不占屏幕 |
| 静默 | 不动鼠标、不抢焦点、不切换前台应用 |
| 举手 | 把某个软件临时置前，仍然用结构化信息操作 |
| 回传 | 后台把"需要用户决定"的事项交回前台 |
| 临时许可 | 用户同意后，后台对某个软件的一次性操作授权 |
