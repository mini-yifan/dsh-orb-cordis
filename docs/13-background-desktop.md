# 后台桌面操作能力 需求文档

> 状态：已确认（2026-11-07 修订：允许操作前台窗口，改为彩带提示）
> 日期：2026-11-07
> 范围：`dsh-orb` 插件（悬浮球 + 后台 agent），不改变前台 Computer Use 模式
> 本文只描述产品形态与需求，不涉及技术实现

## 1. 一句话

让后台 agent 能像人一样操作桌面软件，不碰鼠标、不抢焦点；它操作的每一个窗口都会亮起一条暖色彩带，用户随时看得见是谁在动。它不能向用户提问，做不到的事交回前台。

## 2. 背景与问题

当前悬浮球有两个角色：

- **前台 agent**：Computer Use 模式，能看屏幕、能操作软件，但必须占用屏幕和鼠标，用户只能等它做完。
- **后台 agent**：标准模式，能读写文件、跑命令、上网，**碰不了界面**。

结果是一个长任务被切成两半：后台把文件做完，停下来，通知前台；前台再切回界面部分一步步点。用户看到的就是"它做一会儿、停一下、再动一下"。

问题不在后台不够聪明，在于**后台没有一双手**。

## 3. 目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 后台能独立完成包含界面操作的任务 | 一个"写文档并发出"的端到端任务，全程不需要前台接手 |
| G2 | 后台操作界面时，不打断用户正在做的事 | 用户不切换窗口、不丢焦点、不丢正在进行中的输入 |
| G3 | 用户装完插件即可使用，零额外操作 | 不下载附加组件、不安装运行时、不配置路径、不出现命令行窗口 |
| G4 | Windows 与 macOS 体验一致 | 同样的任务在两边都能完成，用户流程相同 |

## 4. 非目标

- 不改变前台 Computer Use 模式的任何现有行为与体验。
- 后台对界面的理解以软件暴露的结构化信息为主；像素是兜底，不是默认（见 §16）。
- 不突破系统权限：系统不允许的操作就是不允许，不采用非常规手段强行置前或提权。
- 不做远程控制、不做多设备、不做无人工厂。
- 不替用户做不可逆的决定（见 D6）。

## 5. 用户与场景

**场景一：从文档到发出**
用户说"把这份资料整理成 Word，发给张老师"。
后台写完文档，直接在办公软件里打开、排好格式、保存；再在该沟通软件里找到人、附上文件、发出。全程用户可能正在浏览器里看别的东西，屏幕上只有一次短暂的目标窗口置前。

**场景二：批量整理**
用户说"把这批发票按月份归档到对应文件夹"。
后台打开文件管理器，新建文件夹，逐个移动。文件管理器全程在后台，用户不被打扰。

**场景三：做不到的时候**
后台需要操作一个用户正在打字的软件。
它不碰那个软件，先换一条路（改用文件、命令、另一个软件）；都不行，就停下，把"我需要在这个软件里点一下发送，但用户正在使用它"交回前台；前台向用户确认后，或者自己完成，或者给后台一次临时许可。

## 6. 产品形态

- **两个模式并列存在**：前台 Computer Use 模式（不变）、后台桌面模式（新增）。
- **后台模式 = 标准模式的全部能力 + 桌面操作能力**。它仍然是一个可以读写文件、跑命令、上网的工作会话，只是多了一双手。
- **用户通过前台发起**：用户在悬浮球里提出需求，前台判断这段活适合交给后台，就派给后台。用户感知上是"这件事交给它去办了"，而不是"我要手动开一个新模式"。
- **模式在选择器里可见**：用户也能自己新建一个后台桌面模式的会话（不是隐藏能力）。
- **安装即用**：装完插件，两个模式都可用。没有第二次下载、没有安装向导、没有环境配置。
- **平台**：Windows 与 macOS。

## 7. 核心需求

### A. 能力

| 编号 | 需求 |
|---|---|
| A1 | 后台模式必须具备标准模式的全部能力（文件、命令、网页、技能等） |
| A2 | 后台模式必须具备桌面操作能力：查看软件界面结构、点击、输入文本、按键、滚动、等待界面变化、打开/关闭软件、切换窗口 |
| A3 | 后台的操作对象以"软件里的可操作元素"为主：同一元素在不同时刻应能被稳定识别；元素层不可用时才用像素坐标（见 §16） |
| A4 | 界面变化后，旧的定位信息必须失效，不得凭旧信息继续操作 |
| A5 | 动作优先无头；当控件没有语义动作、且它的窗口在最前面时，自动升级为物理输入（真实光标键盘），并在结果里说明 |

### B. 操作与边界

| 编号 | 需求 |
|---|---|
| B1 | **默认静默**：不移动鼠标、不抢键盘焦点、不切换前台应用 |
| B2 | 后台可以操作任何软件，**包括用户正在使用的、位于最前面的窗口**；不需要事先征求许可 |
| B3 | 操作目标窗口时，必须在该窗口四周显示一条彩带（见 C 节），让用户知道此刻是谁在操作 |
| B4 | 同一时刻，同一个软件只允许一个后台任务操作；不同软件可以并行 |
| B5 | 前台模式正在做物理输入（移动鼠标、按键）时，后台不得同时操作同一个软件；其余情况两者互不阻塞 |
| B6 | 后台不得读取剪贴板、系统通知等与当前任务无关的用户内容 |

### C. 彩带

| 编号 | 需求 |
|---|---|
| C1 | 彩带是"后台正在操作某个窗口"的唯一可视信号，默认开启，不提供关闭开关 |
| C2 | 彩带只框住被操作的那一个窗口，不框整个屏幕 |
| C3 | 风格必须与前台的观察框明显区分：前台是整屏的冷色霓虹，后台是暖色的虚线环 |
| C4 | 彩带左上角显示一行小标签，写明"后台操作中 · 软件名" |
| C5 | 彩带不得抢焦点、不得拦截点击、不得出现在截图里 |
| C6 | 最后一条动作结束后保留约 4 秒再消失；同一窗口连续操作时保持常亮，不闪烁 |
| C7 | 目标窗口被其他窗口完全遮住、或系统拿不到窗口坐标时，不画彩带，操作照常进行 |
| C8 | 彩带是提示，不是门禁：画不出来、画失败，都不得阻断动作 |

### D. 举手（临时置前）

| 编号 | 需求 |
|---|---|
| D1 | 举手只用于两种情况：目标窗口没有露出来，或某个控件明确要求窗口在前台 |
| D2 | 举手由后台 agent 自主决定，是一次显式动作，会话记录里可见 |
| D3 | 举手不设空闲门槛：用户正在使用也不阻止 |
| D4 | 举手只把目标软件置前，仍然用结构化信息操作，不移动鼠标、不模拟按键 |
| D5 | 举手是临时的：任务段结束、主动放下、或超时（90 秒）自动放下；放下时把前台还给原本在前的软件 |
| D6 | 举手失败（系统不允许置前）时，不得使用非常规手段强行置前；直接回传前台 |

### E. 不提问与回传

| 编号 | 需求 |
|---|---|
| E1 | **后台模式不包含"向用户提问"的能力**，该能力在后台模式中不存在 |
| E2 | 后台只在"做不到"时停下：没有权限、没有语义动作、软件无响应；"用户正在使用"不再算做不到 |
| E3 | 停下前必须先尝试替代路径：改用文件、命令、其他软件 |
| E4 | 回传内容必须包含：做了什么、卡在哪、为什么需要用户、可选方案、风险提示 |
| E5 | 回传后由前台向用户提问，并决定后续：前台自己完成，或再派一次 |
| E6 | 不可逆操作（发送消息、删除、支付、覆盖保存）不单独拦截，和普通动作一样执行 |
| E7 | 提交类动作（回车、点击发送）成功后，结果必须提示"先确认、不要再按一次" |
| E8 | 同一个动作作用在同一个控件上，若上一次可能已经落地，约 12 秒内必须拒绝重复执行 |
| E9 | 确认的手段是等待或重新观察（等待文本出现、重新快照），不是再执行一次 |

### F. 安装与平台

| 编号 | 需求 |
|---|---|
| F1 | 安装插件后两个模式都可用，不需要任何额外下载、安装或配置 |
| F2 | 全新 Windows 机器（未修改系统安全设置）与全新 macOS 机器上，用户流程一致 |
| F3 | 不出现命令行窗口，不要求用户设置路径或环境变量 |
| F4 | 卸载插件后不留下全局残留 |

### G. 数据与隐私

| 编号 | 需求 |
|---|---|
| G1 | 只读取完成当前任务所需的界面内容；不上传任何界面内容 |
| G2 | 界面内容可能含隐私，日志默认不记录具体内容 |
| G3 | 用户可关闭"后台桌面操作"开关；关闭后后台退回纯文件/命令模式 |

### H. 稳定性

| 编号 | 需求 |
|---|---|
| H1 | 单个界面动作一般在数秒内完成；长时间等待必须对用户可见 |
| H2 | 操作失败不得让任务卡死，必须有超时与明确的失败结论 |
| H3 | 系统不允许的操作不得反复重试刷屏 |

### I. 用户控制

| 编号 | 需求 |
|---|---|
| I1 | 用户能看见后台正在操作哪个窗口（彩带），以及在做什么（会话记录可读） |
| I2 | 用户能随时停止：一个动作停掉当前后台任务，正在进行的界面操作立即中止 |
| I3 | 所有界面操作留痕，可在会话里回看 |

## 8. 状态与规则

| 目标窗口位置 | 用户是否在操作 | 后台行为 |
|---|---|---|
| 前到最前 | 在用 | 直接操作，彩带标出这个窗口 |
| 前到最前 | 不在用 | 直接操作，彩带照常显示 |
| 在后台 | 任意 | 直接操作；彩带画出来但可能被其他窗口遮住 |
| 没有露出来 | 任意 | 无头操作；控件要求前台时才举手 |
| 同一软件已有另一个后台任务 | 任意 | 等待，不得并行操作同一个软件 |
| 前台模式正在物理输入 | 任意 | 等它结束再动同一个软件 |

## 9. 主流程

**流程一：全程后台**

```
前台派活 → 后台读写文件 → 后台在目标窗口里操作（窗口四周亮起暖色彩带）→ 完成后回传结论
```

用户屏幕的变化只有那条彩带。

**流程二：需要前台**

```
后台发现控件要求前台 → 举手 → 窗口置前 → 操作 → 放下并还原前台
```

**流程三：做不到**

```
后台尝试替代路径 → 都不行 → 停下 → 把结论与可选项回传前台 → 前台向用户提问
```

## 10. 用户可见文案（示例）

- 彩带标签：「后台操作中 · 微信」——只说软件名，不暴露界面内容。
- 后台开始处理：「后台正在处理：在 Word 里排版」——出现在会话记录里，不弹窗。
- 举手（窗口被叫到前面时）：「需要把 Excel 切到前面几秒」。
- 交回前台：「这一步做不了：微信没有可操作的无障碍接口。后台已停下，等你决定下一步。」
- 权限/能力不可用：「这台电脑的系统设置不允许后台操作其他软件」。

## 11. 验收标准

1. 用户正在 Word 里打字时，后台任务需要在 Word 里改一段文字 → 后台照常操作，Word 四周出现暖色彩带，用户原有的按键不丢。
2. 后台需要操作一个在后台的 Excel → 直接操作，彩带框住 Excel 窗口（可能被挡）。
3. 后台无头操作被拒绝 → 举手 → Excel 置前 → 用户同时点了一下鼠标 → 后台不中断，彩带继续显示。
4. 后台全程不出现任何提问卡片（该能力不存在）。
5. 最后一条动作结束约 4 秒后，彩带消失。
6. 后台尝试对"发送消息"类动作 → 和普通动作一样执行，不额外停下。
7. 全新 Windows 机器 + 全新 macOS 机器：装完插件即可完成一次"打开软件 → 输入文字 → 保存"的任务，无额外下载。
8. 断网状态下，两个模式都能使用。
9. 会话记录能看到后台操作过哪些软件、做了什么。
10. 关闭"后台桌面操作"开关后，后台无法碰界面，且任务不会因此卡死。
11. 系统拿不到窗口坐标时，动作照常完成，只是没有彩带。
12. 发送按钮没有语义动作、但窗口在前台时，点击会自动升级为物理点击并真正送达。
13. 连续两次对同一个"发送"做同一次操作，第二次被拒绝并提示先确认。
14. 回车提交成功后，模型不会立刻再按一次；它会等待或重新观察。

## 12. 已经定下的取舍

1. **不提供"始终允许"设置。** 不可逆操作也不单独拦截，不再有"先问一句再发"的流程。
2. **彩带默认开启且不可关闭**，只在会话记录之外提供可视提示，不弹通知、不弹卡片。
3. **彩带由后台自己画**：琥珀 → 玫瑰色的虚线环，带缓慢流动与呼吸，左上角一行"后台操作中 · 软件名"。前台模式仍是对的整屏青紫霓虹，两者一眼可区分。
4. **没有"停止"按钮**：用户停任务通过会话里的停止动作完成，彩带本身只做提示、不接收点击。
5. **不再有"用户在用就停"这条规则**，也不再有"离开 60 秒才允许操作"；取代它的是可见性。
6. **无头失败会自动升级为物理输入**，前提是目标窗口在前台；彩带已经标出那个窗口。
7. **重复动作有硬护栏**：同一控件上的同一动作，只要上一次可能已经落地，12 秒内再来一次会被直接拒绝。
8. **提交只做一次**：回车或点发送之后，正确做法是等待或重新观察，而不是再按一次。

## 13. 术语

| 术语 | 含义 |
|---|---|
| 前台模式 | 现有的 Computer Use 模式，占用屏幕与鼠标 |
| 后台模式 | 新增模式：标准能力 + 桌面操作能力，默认不占屏幕 |
| 静默 | 不动鼠标、不抢焦点、不切换前台应用 |
| 彩带 | 后台操作某个窗口时，围在它四周的暖色虚线环与标签 |
| 举手 | 把某个软件临时置前，仍然用结构化信息操作 |
| 回传 | 后台把"做不到"的事项交回前台 |

## 14. 附录：原始对比模式（临时）

模式名「桌面测试（原始 agent-desktop）」，preset id `desktop-raw`。

存在的唯一目的：判断**上游项目本身**在 macOS 上够不够好，还是我们这层包装和护栏把它拖慢了。它刻意违反前面所有产品要求：

- 工具是**未经任何包装的上游命令行**（release 里的 `agent-desktop` + `macos-helper`，版本钉死 1.2.0，校验和与上游一致），直接放到 PATH 上。
- 没有彩带、没有守卫、没有 ref 白名单、没有重复拦截、没有策略升级。
- 物理输入（`--headed`）由模型自己决定用不用，会真的移动鼠标、敲键盘。
- 只有标准模式那套能力，外加这一条命令。

用法：主窗口新建会话时选「桌面测试（原始 agent-desktop）」，然后让它做同样的微信任务，和后台桌面模式对比。

它**不进入任何发布承诺**，只在本机验证；确认结论后可以整块删掉。

## 15. 现状（2026-11-08）：后台模式直通 agent-desktop

前面的彩带、守卫、ref 白名单、重复拦截、前台/后台判定**全部停用**。后台桌面模式现在就是：

- 标准能力（文件、命令、网页、技能、待办、目标）+ **上游原封不动的 `agent-desktop` 命令行**；
- 命令行与 macOS/Windows 二进制随插件包一起分发，首次启动拷到 `~/.dsh/dsh-orb/bin/<版本>-<平台>/` 并加入 PATH；
- 用户装完插件即可用：不下载、不安装、不配路径、不需要命令行窗口；
- 模型先跑 `agent-desktop status`，再读 `skills get desktop` 和 `skills get platform`，之后按上游文档自己决定动作；
- 不再承诺"不动鼠标、不抢焦点"：控件没有语义动作时，模型可以自己决定用 `--headed`。

彩带、守卫、`desktop_*` 工具仍然留在代码里，但没有被任何预设挂载，等于休眠。保留它们是为了以后要回到"受控后台"时不必重写。

这条改动的判断依据是实测：上游 CLI 在微信、QQ 这类 Electron 应用上确实能完成任务，速度和稳定性取决于模型本身（官方 API 明显更稳），而不是取决于我们加的那层包装。

## 16. 现状（2026-11-18）：编排层 + 视觉兜底

§15 淘汰的是**守卫式**包装（彩带、租约、ref 白名单、重复拦截）。那一层被证明是负担，
因为它同时**没有**图片通道、**没有**合步、**没有**动作自带观察——模型只能一步一条 bash。

这次补的是另一类包装：**编排**。它不替模型做决定，只把"该走哪条路、下一步看到什么、
什么时候允许动鼠标"讲清楚。

### 16.1 装配

`preset-desktop` 现在同时挂两行：

- `dsh-orb/desktop/cli-path` — 把 CLI 放上 PATH，保留原始命令通道（§15 不变）；
- `dsh-orb/desktop` — 注册 `desktop_*` 工具。**只复活 `guard.ts`、`frame.ts`、`activate.ts`
  三个模块**；`tools.ts` 里那套彩带/租约工具仍然按需提供，不再是唯一入口。

### 16.2 三层优先级（写进 persona，也写进工具描述）

1. **绕开界面**：文件、命令、URL scheme；
2. **a11y 语义**（默认）：`desktop_status` → `desktop_snapshot` → `desktop_act`，headless、
   不移动指针、不抢焦点；
3. **视觉兜底**：`desktop_see` + `desktop_click_xy`。

降级信号由编排层给出，而不是让模型自己顿悟：

- `desktop_status` 列出目标 App 的窗口，标注 `tree=yes|no`；
- `desktop_snapshot` 在可寻址元素少于 3 个时回答 `tree_thin` 并直接建议转视觉。

目标不唯一、窗口受保护时仍然**硬停下**，不允许盲切坐标（照抄手机端的护栏族）。

### 16.3 `desktop_see`：按窗口取图，不落桌面、不碰剪贴板

- 走 `agent-desktop screenshot --window-id`，**不带路径**，拿到的是 base64 PNG；
- 字节直接进 `attachments.saveImage`，工具结果里是 `{type:'image'}` 内容块，
  与前台 Computer Use 同一条通道；
- 与前台 `screenshot` 工具的区别：**不写 `~/Desktop`、不覆盖剪贴板**；
- 实测（2026-11-18）：本机 158 个窗口里只有 3 个能读 a11y 树；一个
  `visible=false`、`accessible=false` 的 WPS 窗口仍能截到 2940×1612 的图。
  这就是"能在后台完成就后台完成"的技术依据。

### 16.4 `desktop_click_xy`：一张图一次手势

坐标空间是**截图像素**，避开另外两套（前台 CU 的 0–1000、CLI `--xy` 的逻辑屏幕点）。

换算踩过一个坑，必须记下来：**窗口截图包含 macOS 画的投影**，栅格比
`bounds × scale_factor` 大。实测本机常见值是四边各 68 物理像素（2x 下 = 34 逻辑点），
Docker 2676×1576 对 1270×720、QQ 3076×1828 对 1470×846 都是这个差值；个别窗口不同
（DeepSeek Harness 是 112/边），所以 padding 是**按窗口实测反算**的，不是常量：

```
pad = max(0, (raster - bounds × scale_factor) / 2)
```

换算一次折进 `PictureGeometry`（`viewLeft/viewTop` + `pointsPerPixel`），点击时只做乘加。
另一个坑：`attachments.saveImage` 可能缩小栅格，所以 `pointsPerPixel` 用的是**模型实际收到
的图宽**，不是 OS 捕获的宽——否则图缩放后坐标会整体偏移。

这条被 8 个单测和一次真实桌面验收覆盖（2026-11-18：访达窗口 1976×1008、padding 68/68、
画面中心映射回窗口中心误差 0 点）。

护栏族（每条都有单测）：

| 护栏 | 行为 |
|---|---|
| 一图一次 | 点击后立刻作废，失败也作废，防止"再点一次确认" |
| 30 秒 TTL | 过期拒绝，要求重新 `desktop_see` |
| 视口校验 | 窗口位置/尺寸变了即作废，像素不再指向同一控件 |
| 边界检查 | 坐标必须落在图内 |
| 无图不点 | 没有本会话真实返回过的图就拒绝 |
| 动作后不回新图 | 只回文本结论，和手机一致，避免视觉路径无限膨胀 |

`mouse-click --headed` 是**真实物理输入**，官方文档写明它
"never changes focus"——所以它不会把窗口提到前台，这是它比 `focus-window` 更适合后台的原因。
但它无法证明应用接受了这次点击，因此结果一律提示"读完窗口再判断，不要重复点击"。

### 16.5 让每一轮变短的改动

- **动作自带观察**（这一条最关键）：`desktop_act` 成功后，在同一次工具调用里读回同一
  app 的新树并放进结果（`--- <app> now ---` 段），因此"点一下、看一眼"是一轮而不是两轮。
  卡在重复动作护栏上时也回当前树，模型不必再花一轮确认。读回失败**不改判动作结果**——
  动作已经落地，只报告"读不到，请快照"。
  实测（2026-11-18）：一次快照 188–205 ms，而一次模型往返 p50 约 1.9 s，所以多读一次树的
  代价远小于省下的那一轮。6 步序列实测往返数 12 → 6（−50%）。
- persona 要求把"当前树里已可见、互不依赖"的多个动作合成一次 `agent-desktop batch`，
  提交类动作不进 batch；
- 三份引导（`status` + 两份 skill）只在首轮读一次，之后靠 persona 与 `--help`；
- 普通动作可用 `--timeout-ms 0` 跳过库内 5 秒预检，等控件可用的场景除外。

### 16.7 真实运行对比（2026-11-18）

在隔离的 web profile（`bdtest2`，独立端口，不碰用户的桌面 app）里，通过
`typertGateway` 的 `session/create → agentPresets/select(desktop) → commands/execute(/permission) →
session/prompt` 驱动真实 `desktop` preset 会话，run 完再解码会话日志统计。

| 版本 | 任务 | 步数 | 工具调用 | 墙钟 | 推理 |
|---|---|---|---|---|---|
| **基线**（旧版本，QQ 发天气） | 打开 QQ→找我的手机→发消息 | **42** | 43 | **153.5s** | 109.4s (71%) |
| 新版本 · 旧 persona | 计算器 12×34 | 10 | 10 | 27.1s | — |
| 新版本 · 加 batch 指导 | 计算器 12×34 | 15 | 14 | 34.4s | — |
| 新版本 · persona 禁止 bash 操作界面 | 计算器 12×34 | **8** | 7 | **17.5s** | 15.1s (86%) |

基线会话的构成：33 条单命令 bash、**0 次 batch**、6 次 `read_image`（先写 PNG 再读）。

**三次运行各修掉一个真问题**：

1. 第一次：模型在第 5 步正确判断 `tree=no` 并调了 `desktop_see`，但随后改用 `osascript`
   发送按键绕过界面。→ persona 明确：界面只用 `desktop_*`，bash 不做 GUI。
2. 第二次：模型从 CLI 的 skill 文档里学到 bash 那套，`desktop_*` 和 bash CLI 混用。
   → persona 把"读指南"改成"仅在 level-2 无法解释地失败时才读"，并声明本 prompt 优先于指南。
3. 第三次：工具序列干净（`desktop_apps → desktop_snapshot → desktop_status → desktop_see →
   desktop_raise → desktop_see`），**只有 1 次 bash 且是查电源状态**。

**「动作自带观察」在真实运行里确认生效**：`desktop_act` 的返回里有
`--- 计算器 now ---` + 26 refs 的新树，模型下一条动作直接用新 ref，没有插入 `desktop_snapshot`。

**这次运行没能完成点击**，原因是环境而非代码：`APP_UNRESPONSIVE: CoreGraphics returned no
active displays`——显示器已休眠，截图取不到。同样的命令在终端里也如实返回这个错误，
说明是 TCC/窗口服务器状态，不是工具缺陷。**因此 17.5s 是"能跑完的工具链耗时"，不是
"完整 QQ 任务"的改后数字**；真正的同任务对比仍需要在一台醒着的机器上重跑基线那条 QQ 任务。

同时修掉两个真实缺陷：

- `listWindows` 直接读 CLI 原始 JSON（snake_case），导致 `<window>` 显示 `undefined`；
  现在归一化 `app_name → appName`。
- `desktop_status` 原来走 FFI 的 `op:'windows'`，而 FFI 窗口记录**没有** accessibilty 位、
  且按 OS 显示名过滤（"Calculator" vs "计算器"匹配不上），于是窗口段常常是空的——
  模型只能靠 `desktop_snapshot` 的报错猜。现在改走 CLI 并做宽松名字匹配，`tree=no`
  提示能稳定出现。

### 16.6 仍未解决

- **四套锁互不知情**：`gui-lock`、`guard.leases`、CLI 的 per-user `interaction.lock`、
  `screen-owner`。物理点击目前不过 `gui-lock`，与前台模式并发时可能互相干扰。
- **无人值守没有批准点**：`desktop_click_xy` 不做"人是否在场"判断。远程派发
  （`incomingPreset: desktop`）场景下它会真的移动鼠标，而没有人能看见。
- **Windows 缺 per-HWND 捕获**：macOS 可按窗口 ID 独立截图，Windows 目前只有屏幕矩形。
- **视觉不等于更快**：QQ 实测里两次 12–20 秒的长推理都发生在看图之后。视觉解决的是
  "点得中"，提速靠的是 batch 与减少往返。

### 16.8 复现这套测量

`packages/desktop/scripts/measure-desktop-task.mjs` 是上表用的驱动脚本。它作为一个
cordis 插件加载进任意 profile，等 `typertGateway` 与 `sessionController` 就绪后：建会话 →
选 `desktop` preset → 设 `danger-full-access` → 发任务 → 轮询会话日志直到 `turn/end` →
打印 `MEASURE {...}` 与步数/工具/墙钟。

跑法：

```bash
# 1. 准备一个装了本 bundle 的 profile（会写入 ~/.dsh/profiles/<name>）
dsh plugin --profile measure add <repo>/packages/bundle
# 2. 在该 profile 的 cordis.patch.yml 里插入驱动插件
#    - insert:
#        - id: measure
#          name: 'file://<repo>/packages/desktop/scripts/measure-desktop-task.mjs'
# 3. 起 profile 并给出任务
MEASURE_TASK="打开计算器，算 12 乘以 34" MEASURE_CWD=/tmp dsh --profile measure --no-open
```

前提：**显示器必须醒着**。睡眠时截图返回
`APP_UNRESPONSIVE: CoreGraphics returned no active displays`，任何依赖视觉的任务都会失败；
`agent-desktop list-displays` 会返回空数组，可用来先自检。

要拿同任务的对等对比，把基线那条任务（打开 QQ → 找到"我的手机" → 发送天气）用同一脚本
跑一遍，比较 `steps` / `toolCalls` / `wallMs`。

### 16.9 同任务实跑（2026-11-18 晚，锁屏状态下）

用 §16.8 的脚本，把**基线那条 QQ 任务**原样跑在新版本上。两次运行都在 `desktop` preset
下真实执行，会话日志解码统计：

| 运行 | 步数 | 工具调用 | 墙钟 | 推理 | desktop_* 调用 |
|---|---|---|---|---|---|
| **基线**（旧版本，2026-11-14，电脑解锁） | **42** | 43 | **153.5s** | 109.4s (71%) | 0（全是 bash 调 CLI） |
| 新版本·锁屏·无锁屏检测 | 35 | 37 | 233.2s | 118.5s (51%) | 21 |
| 新版本·锁屏·**有锁屏检测** | **9** | 9 | **81.4s** | 18.0s (22%) | 2 |

**这两次新运行不是完成态数据，这一点必须说清**：运行时这台 Mac 处于锁屏
（`CGSSessionScreenIsLocked = True`，前台是 `loginwindow`）。锁屏时窗口服务器不返回任何
窗口信息，`list-windows` / `screenshot` / ref 动作全部超时，所以任务**不可能**完成。
第一次 35 步里，模型花了 6 条 bash 自己去排查（`Quartz`、`pmset`、`ioreg`、`caffeinate`、
`screencapture` 挨个试），才确认是锁屏。这是工具的失败模式不够清楚造成的浪费，不是模型笨。

修法：`desktop_status` 现在用 `CGSessionCopyCurrentDictionary` 读锁屏状态，锁屏时直接给出
`screen locked: yes` 加一段"停止、别重试、去走不需要屏幕的路径"的明确指令；`desktop_see`
同样在入口就返回 `SCREEN_LOCKED`。改完再跑同一任务：**35 步/233s → 9 步/81s**，
`desktop_*` 调用从 21 次降到 2 次，模型一次就读懂了，把天气查好、草稿写好、明确报告
"屏幕锁着，需要你解锁"。两次运行都**没有**尝试绕过锁屏（没有猜密码、没有改安全设置）。

**因此，与 153.5s 的对等比较仍未取得**：那需要一个解锁且活跃的桌面。可用的对等数据是
"同一任务、同一 preset、锁屏前提下"的 233.2s → 81.4s（−65%），它衡量的是失败路径的效率，
不是任务本身的完成耗时。要拿到完成态数字，请在电脑解锁时执行 §16.8 的重跑命令。

### 16.10 锁的两处收口（2026-11-18）

**坐标点击现在过共享的 GUI 锁。** `gui-lock.ts` 读的是
`Symbol.for('dsh-orb.gui-lock')`——和 Computer Use 用的同一个符号。前台会话在移动指针、
拍摄动作后截图期间持有它，后台 worker 的 `--headed` 点击碰的是同一块屏幕，所以两边必须
互斥。之前 `desktop_click_xy` 完全没读这把锁，可以和前台 CU 的点击交错。争用同样
fail-fast，不发排队点击（排队会让点击在瞄准时刻之后才落下）。失败时图片照样作废，
不会变成重试循环。

**物理点击默认关闭。** `preset-desktop` 现在显式配 `coordinateClick: false`：后台 worker
判断不了机器前有没有人，无人看管的点击会真的移动用户的鼠标。坐在电脑前用的时候把它
打开即可；关着时 `desktop_click_xy` 返回 `COORDINATE_INPUT_OFF` 并指向 a11y 路径。

6 条新测试钉住互斥：他人持锁时拒绝且不投递、自持可重入、抛错也释放、成功后释放、
匿名调用者同样不能插队。

## 17. 现状（2026-11-18 深夜）：视觉优先，辅助功能退为备选

§16 的所有改动都建立在同一个前提上：**辅助功能树是主路径，看图是兜底**。这个前提被一次
真实运行证伪了。

### 17.1 证伪它的那次运行

同一条 QQ 任务（打开 QQ → 进"我的手机" → 发一条消息），`desktop` preset，解码
`session-75b8dd0b`：

| 指标 | 值 |
|---|---|
| 墙钟 | **173.9s** |
| 步数 | **55** |
| 工具调用 | 57（其中 48 次 `desktop_*`） |
| 模型时间 | 121.1s（70%），即**每步 2.2s** |
| 调用分布 | `desktop_snapshot`×17 `desktop_act`×14 `desktop_status`×9 `bash`×7 `desktop_see`×3 `desktop_raise`×2 `desktop_click_xy`×1 `desktop_wait`×1 `desktop_release`×1 |

同一个模型、同一条任务，Computer Use 模式 **23s / 约 8 步**。每步的思考耗时几乎一样
（CU 约 2.9s，后台 2.2s），所以差距 **100% 来自轮次**：55 vs 8。工具延迟不是瓶颈，实测
`list-windows` 0.23s、`screenshot --window-id` 0.31s、`screencapture -o -l` 0.05s。

55 步的去向：

1. **步骤 1–6（22s）**：真正在干活，找到 QQ、读到树、定位到 `我的手机`。
2. **步骤 7–32（78s，26 步）：在跟"点击"搏斗。** 步骤 24 调 `desktop_see`，模型**一眼**就把
   窗口描述对了（"QQ NT 客户端，左侧图标：消息/联系人/空间/频道…"）。步骤 25 调
   `desktop_click_xy` → `COORDINATE_INPUT_OFF`——因为 §16.10 在 preset 里写了
   `coordinateClick: false`。模型据此判定"物理点击不可用"，用 22 秒重建了整条 a11y 路径。
3. **11 步 / 约 35s：raise/lease 舞蹈。** `desktop_act` 的物理回退要求窗口在前台 →
   "physical fallback denied because window isn't in front" → `desktop_status` →
   `desktop_raise` → `desktop_status`；后来用户碰了机器（DSH 到前台），租约失效 →
   `status` → `wait` → `status` → `raise` → `snapshot` → `act`。
4. **约 5 步**：天气 API 考古（反复换源），与工具无关。

**任务在 108s 时已经完成**（消息已发出），后 66s 是补一条更正 + 重新校验 + release。
另外，`desktop_act` 每次回传的树都是"4 个 ref"的空壳，模型反复怀疑"是不是新窗口开了"，
于是 `desktop_status`×9、`desktop_snapshot`×17——**一个不可信的观测比没有观测更贵**。

结论：不是"视觉比辅助功能准"，而是**辅助功能路径把一次点击拆成了两个轮次，并且在坏天气里
额外收了 3–5 个轮次**。QQ 这类 Electron 客户端的主窗口本身几乎没有可用的树。

### 17.2 新工具面：沿用 Computer Use 的手势集

第一版把 8 个动作压进了一个 `desktop` 工具（`action: see|click|...`）。形状能跑
（25 步那次没有任何参数错误），但它是错的形状：Computer Use 好用的地方正是**一个手势一个
工具**——工具名就是意图，每个工具的参数表只包含它自己用得上的字段。把它们塞进一个联合
参数表，模型要同时记住 13 个字段里哪 5 个属于当前动作，UI 上也只剩 `desktop {...}`。

所以现在是同一套手势、同一个命名习惯：

| 工具 | 作用 |
|---|---|
| `desktop_open_app` | 启动或激活一个 app，返回它的窗口图 |
| `desktop_see` | 看一眼（CU 不需要它，因为 CU 一开场就注入首帧；后台模式不注入，所以要有显式的看） |
| `desktop_click` | 点一个 0–1000 位置，返回新图 |
| `desktop_input_text` | 输入文字（可先点一下聚焦、可 replace、可 submit），返回新图 |
| `desktop_hotkey` | 按组合键，`keys` 是数组（`["cmd","c"]`，不会解析错） |
| `desktop_scroll` | 在某点滚轮，返回新图 |
| `desktop_drag` | 从一点拖到另一点，返回新图 |
| `desktop_wait` | 等一下再取图 |
| `desktop_inspect` | 读辅助功能树，给出 ref |
| `desktop_act` | 按 ref 执行（14 种语义动作），headless，不动指针不抢焦点 |

删掉：`desktop_status`、`desktop_apps`、`desktop_raise`、`desktop_release`、
`desktop_click_xy`。原来的 `desktop_snapshot` 改名为 `desktop_inspect`。

和 CU 有意保留的两处差别：每一处都多一个 `window` 参数（后台 worker 通常是被指定了 app，
而不是接管用户眼前的窗口）；没有 `open_in_browser` / `open_in_finder` / `long_press`
——前两个就是 `open` 一条 shell 命令（第 1 层），第三个在桌面上几乎用不到。

"窗口在前台吗 / 这个 app 有哪些窗口 / 刚才成功了吗"这三个问题，现在都由每个结果里那行
`window QQ w-35248 720x640 front=yes tree=no` 和它附的图回答。

顺带补上 CU 有、第一版漏掉的一件事：**动作后等一拍再拍图**（`postActionWaitMs`，默认 400，
preset 里按 CU 设成 600）。点击会立刻返回，app 还没画完；立刻截图递给模型的是一张半成品，
它会对着还在移动的控件瞄。

### 17.3 四条让一轮变短的规则

1. **一个动作 = 一次调用 = 一张新图。** 动作的返回值里就带着动作后的窗口，所以一次点击是
   一个轮次，不是两个。这是手机的 `after()` 落到桌面上。
2. **点是 0–1000 的比例，相对"你刚拿到的那张图"。** 不是像素，不是屏幕坐标。模型不做任何
   换算，也就不需要知道 `scale_factor`、窗口矩形、阴影 padding。副作用：attachment store
   把图缩小也不影响映射（比例天然缩放无关）。
3. **指针动作先把窗口提到前台。** 原因：`mouse-click --xy` 是绝对屏幕坐标，窗口在后面
   时点击会落在最上层的东西上。所以 `ensureFront` 在工具内部完成，模型不用管 raise/release。
4. **失败时附带新图。** 点系在一张旧图上，而旧图过期/属于别的窗口/窗口移动过时，纠正所需
   的一切都在同一个结果里返回，重试不额外花一个轮次。

阴影 padding 仍然要算（macOS 在窗口矩形外画了投影），但只在 `frameOf()` 里算一次，
模型永远看不到这些数字。

### 17.4 坐标打字：粘贴，然后还原剪贴板

`agent-desktop type` 必须给一个 ref，所以一个没有辅助功能树的窗口根本没法输入文字——这是
纯视觉流程唯一补不上的洞。`hid.ts` 用 Computer Use 的老办法补：把文本放到剪贴板 → `Cmd-V`
→ 把**每一种类型**的剪贴板内容原样写回（不只是字符串，图片和文件列表也是 NSData）。
`type` 动作因此可以 `point` + `text` 一次调用完成，和 CU 的 `input_text` 一样。

剪贴板还原是这段代码里唯一会破坏用户数据的地方，所以有一个直接验证：把剪贴板设为
`ORIGINAL-CLIPBOARD-VALUE`，跑一遍带还原、不带按键的脚本，`pbpaste` 仍然返回原值。

限制：只有 macOS 有这条实现。Windows 上 `type` 返回 `PLATFORM_NOT_SUPPORTED`，把模型指向
`desktop_inspect` + `desktop_act`。

### 17.5 persona 与 preset 的变化

- `preset-desktop` 的描述改成"看图定位、点哪打哪，辅助功能树作为备选"；
- persona 的三层优先级改成：(1) 不走界面 → (2) `desktop` → (3) `desktop_inspect` + `desktop_act`；
- 明确写"点击会把窗口提到前台、会移动真实指针，这是预期行为，不要因此停下或道歉"；
- 删掉"读 `agent-desktop skills` 指南"那一段——它是在鼓励模型用 bash 碰 GUI，和同一条
  persona 里的禁令自相矛盾；
- preset 里的 `coordinateClick: false` 删除，`config.coordinateClick` 和
  `config.physicalFallback` 一起删除（后者的物理升级也删了：物理输入现在只有 `desktop` 一条路）。

**悬浮球 agent 的提示词一个字没动。** 这样它把活交给本机后台 agent 时，仍然只是"干活"；
只有别的设备把任务送进来时，落地的 `desktop` preset 才既有干活能力又有操作电脑的能力。

### 17.6 代价，写在明处

视觉 = 前台。点击落在最上层窗口、光标会动、用户同一时刻不能用这台机器。§16 里那套
"不打扰用户"的机制（idle 判断、90s 归还、per-app 租约）在视觉优先下只剩成本：这次运行里
它触发了两次，每次都多花 2 个轮次。所以它被拆掉了，只保留 `guard.ts` 里"同一个 app 同时
只有一个会话在操作"这一条（a11y 路径用）。

这是一次明确的取舍：**用户说可以打扰，不再为礼貌付轮次。**

### 17.7 还没验证的

- 新的 `desktop` 路径**没有跑过真实任务**。用户明确要求实跑由他来做，这里只交代码。
- macOS 的 `Cmd-V` 粘贴链路（`chord` / `tapKey`）来自 Computer Use 的同一段 JXA，剪贴板
  往返已验证，但"粘贴 + 回车"的端到端还没在真实窗口里跑过。
- Windows 上没有按点打字，也没有按窗口截图的独立实现（仍是 CLI 的 `screenshot --window-id`）。

### 17.8 第一次实跑：25 步 / 103s，其中 78 秒是我的 bug

`session-98a7962b`（"往 QQ 我的手机发当前时间"）：**103.3s / 25 步 / 模型 63.9s**，
`desktop`×15、`bash`×9、`desktop_inspect`×1。**任务在重启 QQ 之后只用 5 步 25 秒就完成了**，
也就是说交互层已经到位；前 78 秒全部花在一个"无法聚焦的 QQ"上。

原因是我把一件设备事实当成了没有事实：

**QQ 有 13 个窗口，同一时刻只有一个在屏幕上。**（实测：`w-35573` 1470×846 可见，
其余 12 个 `visible=false`——1×1 渲染器、1920×30 菜单栏条、1470×33 标签条，还有几个
720×640/800×600 的隐藏渲染面。）当 QQ 主面板收进菜单栏时，之前那次运行里**唯一在屏幕上的
窗口是 QQ 的内置浏览器**（标题 `QQ(窗口)`，树里是 `webarea "QQBrowser"`）。

三个 bug 把这件事变成了瞎找：

1. **`launch` 按面积挑窗口**，不看 `visible`。于是"QQ 已启动"配了一张浏览器图。
2. **`other QQ windows` 把 12 个隐藏窗口和 1×1、1920×30 的辅助面一起列出来**，模型照着点了
   四次（`w-35001` 350×510、`w-32724` 1920×30、`w-35248` 720×640 空图），全是不可见的。
3. **`focus-window` 对隐藏窗口失败**，返回的是 "Window focus did not settle"，读起来像传输
   故障，模型因此怀疑"焦点机制坏了"，继续换窗口试了 3 次。

修法：

- `visible=false` 的窗口**不再自动选中**，也不再出现在 `other … windows` 里；
  小于 120×80 的窗口（菜单栏条、1×1）同样排除。显式点名的窗口仍然照常返回，
  所以 `see window=…` 还能看到"这张图是空的，因为它不在屏幕上"。
- `launch` 只接受**在屏幕上**的窗口。如果一个 app 有窗口但一个都不在屏幕上，
  1.5 秒后就直说：*"QQ 在运行但没有窗口在屏幕上（13 个窗口全不可见）。它被最小化了，
  或者收进了菜单栏。从 Dock/菜单栏打开它，或者退出重开，然后 action=see。"*
  这句话本来能省掉整段 78 秒。
- `focus-window` 失败且窗口不在屏幕上时，给出的解释是上面那段，而不是 "focus did not settle"。
- 窗口行现在带标题：`window QQ w-35573 1470x846 front=yes tree=yes title="QQ(窗口)"`。
  标题往往就是"这是聊天面板还是它自带浏览器"的唯一线索。
- 坐标回显从 `164%,387%` 改成 `(164,387)`——那个 `%` 让人以为输入是百分比。

顺带确认：`visible` 是动态的（终端应用最小化、显示器休眠都会让它变 false），所以诊断文案
列的是全部可能原因，而不是断定"这是隐藏辅助窗口"。

测试新增 4 条：隐藏窗口不被自动选中、隐藏窗口不列出、上次的窗口一旦离屏就放弃、
显式点名的隐藏窗口仍然返回（这样 `see` 能解释空图）。

## 18. 官方 Computer Use 是怎么做的，以及我们抄了什么（2026-11-18 晚）

### 18.1 那个 session 不是我们的工具

`session-ccfdb3d5` 里 **52 次调用全是 `run_code`，上下文中一张截图都没有**。它跑的是 DSH
自带的 `@deepseek-ai/dsh-cua`，接在 `ptc` preset 上：

```js
var cu  = connectCua(() => tools.cua)
var app = await cu.getApp("27997")
var win = await app.getWindow(35573)
var tree = await win.getAccessibilityTree({ maxElements: 3000, maxDepth: 40 })
await app.setValue("685", "现在是 2026年11月18日 15:03:14")
await app.pressKey("Return")
```

三个机制让它看起来快：

1. **观测是文本**。AX 树当字符串返回，模型自己在里面 grep、切片、按 `[133]` 取上下文，
   全部在一个单元格内完成。
2. **一个 `run_code` 里串很多动作**。读树 → 点 → 重读 → 写值 → Return → 再读 → 截图核对。
3. **树写到文件再查**。它执行过 `tools.write("/tmp/qq_tree.txt", qtree2)`，之后反复 grep
   那个文件，而不是每轮把三万字重新塞进上下文。

### 18.2 按任务量出来的真实差距

同一条 session 有三个 turn：

| turn | 任务 | 墙钟 | 步数 | 每步 |
|---|---|---|---|---|
| 1 | 默认浏览器改成 Safari（系统设置） | 81.8s | 22 | 3.7s |
| 2 | QQ 发当前时间 | 59.2s | 15 | 3.9s |
| 3 | QQ 发青岛天气 | 162.2s | 18 | 9.0s |

我们：发当前时间 103.3s / 25 步（其中 78 秒是 §17.8 那个窗口可见性 bug，修完那 5 步 25 秒）；
发天气 173.9s / 55 步。

**结论要诚实：发天气那条它并不比我们快（162 vs 174）。它快在步数少三倍——每步干得多。**
我们每步 2.2–3.2 秒，它每步 3.7–9 秒。总时长被网络和 app 状态主导，步数差异才是体感来源。

### 18.3 决定：不挂 PTC，改树优先，两个平台都要能用

PTC（`run_code`）是它步数少的主因，但用户明确不要把它挂到后台桌面 preset 上。于是剩下两个
能做、也确实该做的：

**1. 树优先。** 官方是 AX 优先、坐标兜底；我们是反过来的。改回来之后：
- `desktop_inspect` 成为**入口**：自己解析窗口（点名的 → app 的 → 前台的），第一行给出
  `window QQ w-35573 1470x846 front=yes tree=yes`，然后才是树。
- `tree=no` 时**不做读**，直接说"这个窗口没有可寻址的元素，用 desktop_see + 坐标工具"，
  不再付一次 `ACTION_NOT_SUPPORTED`。
- `desktop_act` 一个动作带回新树，所以树路径上**一个动作是一轮**。
- 写字段优先 `set_value`：不碰剪贴板、不抢焦点、一次调用。

顺带解决了一个老问题：以前要拿到 window id 必须先 `desktop_see`（就是要付一张图）。
现在 `desktop_inspect` 自己就有 window id。

**2. 两个平台。** 之前按点打字是 macOS 专属（JXA 粘贴）。现在 `desktop_input_text`：

| 平台 | 顺序 |
|---|---|
| 任意 | ① 用 CLI `find` 找聚焦/第一个文本控件 → `type @ref --stdin`（语义插入，不碰剪贴板） |
| macOS 兜底 | ② 没有可寻址输入框 → JXA 粘贴，**并把剪贴板每种类型还原** |
| Windows 兜底 | ② 没有可寻址输入框 → 明说做不到，指向 `desktop_inspect` + `desktop_act` |

Windows 上刻意**没有**做剪贴板粘贴兜底：DSH 的 Windows 剪贴板快照是 koffi + Win32 原生代码
（`packages/computer-use/src/windows-native.ts`，约一千行），照抄进 desktop 包不划算，而
"清空剪贴板"是不可接受的副作用。

其他平台审计：`session-state`（非 darwin 直接返回未锁定）、`activate`（有 PowerShell 分支）、
全部 GUI 手势（都是 CLI 子命令）、`native-paths`（`win32-x64` / `win32-arm64` 都在打包内）。

**Windows 唯一的功能缺口**写在 `desktop_act` 的描述里：Windows 上"重复出现的控件"（相同的
行、相同的按钮）**没有 ref 路径**——CLI 只在"窗口里该角色+名字唯一"时才解析 ref。那种行
只能靠 `desktop_see` + 坐标点。
