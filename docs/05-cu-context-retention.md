# 需求文档：Computer Use 模式长任务响应缓慢的治理

## 1. 背景

### 1.1 现象

Computer Use 模式下，一轮任务中模型调用 GUI 工具几十次以后，每一步的响应明显变慢；调用七八十次之后基本不可用。关闭深度思考也只有小幅改善。

### 1.2 数据（660 份会话日志）

按"会话内累计截图数"分桶统计每步耗时：

| 会话内累计截图 | 每步中位耗时 | 每步 p90 |
|---|---|---|
| 0 张 | 4.3 s | 19.3 s |
| 20+ | 5.1 s | 15.7 s |
| 40+ | 8.5 s | 26.4 s |
| 50+ | 10.4 s | 30.0 s |
| 70+ | 8.2 s | 35.0 s |
| 80+ | 7.5 s | 38.2 s |

两组对照会话：

- `session-a6a1ddc0`：60 步 / 73 次工具调用，但几乎不产生截图，全程稳定在 2–10 s。
- `session-5bfeac59`：266 次工具调用 / 233 张截图，每步一张。

### 1.3 问题定性

每一次 GUI 工具调用都会多产生一张截图，进入历史、之后每一步都重新发给模型，只增不减。截图越多，每步输入越大，响应越慢。**当前的判断：拖慢响应的是每步一张截图的累积，而不是循环次数本身。**

### 1.4 现有证据的边界（知情项）

以下三点是当前数据还不能回答的，直接影响本需求的范围与收益，实施前需要先补数据：

1. 中位耗时在第 50 步左右见顶后没有继续恶化，"截图越多越慢"可能不是唯一因素，也可能与不同会话的任务类型混杂有关。
2. 数据未按所用模型、任务类型分层。
3. 没有"调用次数很多但不产生截图"的长会话数据，因此无法排除文字历史增长同样在拖慢响应——这决定需求三是否必要。

---

## 2. 目标

- **G1**：Computer Use 会话的视觉上下文有明确上限，不随工具调用次数无限增长。
- **G2**：单步耗时封顶，不随任务推进持续恶化。
- **G3**：不损害用户的界面体验与历史记录：翻看历史时截图照旧可见，会话恢复行为一致。
- **G4**：只治理 Computer Use 模式，不影响其它模式与普通会话。

---

## 3. 需求一：截图历史封顶

### 需求是什么

给 Computer Use 会话的截图历史设置一个数量上限。超过上限后，**最老的截图不再发给模型，改由一段固定的占位文字替代**；用户的界面、历史记录、会话恢复完全不受影响。

### 规则

1. 上限按"仍可发给模型的截图张数"计，暂定 25 张（评审区间 15~30，最终值由评审确定）。
2. 未超过上限时，行为与现状完全一致，不得引入任何变化或额外开销。
3. 超过上限后，每产生新截图，淘汰当前最老的一张；一步产生多张时，允许一次淘汰多张，使未淘汰数量回到上限以内。
4. 淘汰方向必须始终是"当前最老优先"，淘汰点在时间轴上单调前移；已淘汰的截图永不恢复。
5. 淘汰只作用于发给模型的内容：
   - 界面：用户翻看历史时所有截图照旧可见；
   - 日志：原始截图记录保留，恢复会话与回放行为与现状一致。
6. 被淘汰截图的位置，模型看到的是一段固定占位文字；同一张截图的占位文字在所有后续请求中逐字节一致（不得含时间戳等会变化的内容）。
7. 模型若确实需要看更早的画面，只能重新截一张（多一次工具调用）。这是本需求接受的代价。

### 用户可感知的变化

- 截图数未超上限前：无任何变化。
- 之后：长任务的每步响应不再持续变慢，趋于稳定。
- 界面与历史回看：无变化。
- 代价：模型丢失对更早画面的记忆；连续精细操作（画图、拖拽）类任务成功率可能下降、需要返工。

### 完成标准

- 一个 ≥40 次 GUI 调用的会话：任一时刻发给模型的截图数 ≤ 上限 + 本步新增。
- 同会话：第 50 步的单步中位耗时不超过第 10 步的 1.5 倍，p90 同样不再随步数上升。
- 界面回归：历史截图逐张可见，与改动前一致。
- 日志回归：恢复会话 / 回放后行为与改动前一致。

## 4. 需求二：同一步的多次截图只保留最后一张

### 需求是什么

模型在一步内可以连续调用多个 GUI 工具（例如画图时连续拖拽十几次）。目前每次调用后都会产生一张截图，一步可能积累十几张。要求**同一步内只保留最后一次操作产生的画面，中间状态的截图不再发给模型**。

### 规则

1. 每一步的最终画面必须保留（多屏会话按每个屏保留）。
2. 同一步中间状态的截图不进入发给模型的内容；本步实际发生的操作及其文字结果（点了哪里、拖到哪里）照常完整记录，不受影响。
3. 只产出一张截图的普通步骤（单击、输入等），行为不变。
4. 模型在一步进行中看不到自己刚操作的中间状态（下一步请求时才看到本步最终画面）。这是本需求接受的代价。

### 用户可感知的变化

- 批量拖拽 / 画图步骤：发给模型的截图从十几张降为 1 张。
- 每一步仍然带有一张最新的屏幕画面，模型不会"失明"。
- 中间截图是否仍在界面上保留，待 §6 确认事项给出结论；在得出结论前，不得默认界面"完全不变"。

### 完成标准

- 批量拖拽步发给模型的截图数 = 1（多屏则乘以屏数）；普通步 = 1。
- 同一步的操作记录与文字结果不丢失。
- 下一步请求中，模型能看到本步的最终画面。

## 5. 需求三：Computer Use 更早触发历史压缩（条件性）

### 需求是什么

Computer Use 会话的文字历史（工具调用记录、命令输出、用户消息）增长到约 15 万 token 时，自动触发一次历史压缩：把更早的对话折叠为一段摘要，保留最近部分，对话继续进行，防止纯文字历史无限增长拖慢响应。

### 前置条件

1. 只作用于 Computer Use 模式，不影响其它模式与普通会话。
2. 本需求是防御性的：需求一、二负责视觉侧。若二者实施后长任务劣化已解决，本需求可以不做；是否立项取决于"文字历史也是劣化来源"的实测结论（§6 确认事项 1）。

### 用户可感知的变化

- 触发的那一步会明显卡一次（需额外调用一次模型写摘要，可能几十秒到一分钟）。
- 触发后更早的历史折叠为摘要，用户看到历史被折叠；之后每步响应回落。
- 文字记忆的要点保留，细节会丢失。

### 完成标准

- Computer Use 会话在约 15 万 token 处触发自动压缩。
- 其它模式的触发阈值与行为无变化。
- 不因配置问题导致 Computer Use 模式加载失败或会话报错。

---

## 6. 待确认事项（实施前需要结论）

1. **分层数据归因**：按所用模型、任务类型、图 / 文构成，复测每步耗时，确认文字历史是否也是劣化来源——直接决定需求三是否立项。
2. **中间截图的界面保留方式**：确认需求二能否在"界面仍保留中间截图"的前提下只对模型隐藏，以及做不到时对界面的影响是否可以接受。
3. **需求二可行性**：确认同一步内的多次截图能否在生成环节就截断，评估工作量与外部依赖。

---

## 7. 实施优先级

需求一 → 需求二 → 需求三（条件性）。

需求一与需求二互相独立、收益互补，可分别实施；需求三以前两项的实测结果为前提。
